# Append-only ECATSL repository with durable SQLite replay

Task 2.2 introduces typed append-only persistence, specialized candidate/policy/validation/classification projections, and durable idempotency records. The public generic path can bypass every projection and persist a confirmed classification directly. A second route accepts caller-constructed `PathEvidence` as adapter proof, while policy and finding writes roll back decisions that the requirements say must survive metadata failure. **Watch for:** **Critical · confirmed** generic projection/confirmation bypass; **High · confirmed** self-asserted static-path authority; **High · confirmed** loss of successful policy and classification decisions on metadata-write failure.

## High-level view

**Critical · confirmed:** `persist_artifact` accepts any `Artifact` subtype and writes only `ecatsl_artifact`. Passing a candidate, policy decision, validation result, scope/reuse revision, or finding classification through it avoids the corresponding projection and lineage checks; a `CONFIRMED` `FindingClassification` therefore needs neither `persist_classification` nor `PathEvidence`.

**High · confirmed:** the specialized classification gate verifies that the referenced row deserializes as `PathEvidence` and has a non-blocking sanitizer, but adapter support is only a caller-supplied `Literal[True]`. The focused positive test constructs that object directly and stores it through the generic API, so no retained adapter execution or supported-adapter registry authenticates the proof origin.

**High · confirmed:** policy outcomes and finding classifications share all-or-nothing transactions with their audit/lineage projections. Any metadata failure rolls the decision back, contrary to Requirements 3.9 and 4.7, which require the successful decision to remain with explicit missing-element flags.

**Medium · confirmed:** finding lineage is both lossy and weakly typed. Only the first specification identity reaches `ecatsl_finding_lineage`, and specification/explanatory-support IDs are checked only as generic artifacts rather than as `ConstrainedDeclarativeSpecification` and catalog-support records.

**High · confirmed:** replay and untyped `load` resolve the Python module and qualified class name stored in SQLite by importing it. A corrupted local database can trigger imports before the code establishes that the stored type is an allowed ECATSL model, and ordinary model moves or renames make durable replay unreadable.

**Medium · confirmed:** schema v2 is tested only as part of a fresh install over a legacy catalog. There is no historical schema-v1 database fixture upgraded to v2, so checksum compatibility and preservation of populated v1 ECATSL rows are not protected against future edits to the frozen v1 migration.

## Generic persistence bypasses all semantic projections

**Critical · confirmed.** `persist_artifact` at `src/ecatsl/artifact_repository.py:274-285` calls `_insert_artifact` and records idempotency without dispatching or rejecting projection-bearing models. The checks in `create_candidate`, `persist_policy_outcome`, `retain_validation`, and `persist_classification` are therefore optional API conventions rather than repository invariants. A caller can pass a `FindingClassification(status=CONFIRMED)` directly to `persist_artifact`; it is committed without the checks at `artifact_repository.py:583-600` and without an `ecatsl_finding_lineage` row. Candidate/policy/validation/scope/reuse artifacts can likewise exist in the base table while being invisible to head checks and relationship queries.

Restrict the generic method to artifact kinds that intentionally have no projection, or make it a closed dispatcher that invokes the specialized operation for every projection-bearing subtype. Add negative tests for generic candidate, policy, validation, classification, scope, and reuse writes, including a direct confirmed-classification attempt.

## Self-asserted PathEvidence can satisfy confirmation

**High · confirmed.** `PathEvidence.supported_adapter` is merely `Literal[True]` in `src/ecatsl/models.py:222-231`; any caller able to instantiate the model supplies that assertion. `persist_classification` at `artifact_repository.py:589-599` checks the stored Python type and sanitizer status but does not verify an adapter allowlist, a retained supported-adapter run, a matching static `ValidationResult`, or binding among the path, candidate, and specification. The positive repository test demonstrates the production path at `tests/unit/ecatsl/test_artifact_repository.py:295-344`: it manually constructs `PathEvidence`, writes it with `persist_artifact` at line 329, and then confirms against it.

Introduce a dedicated static-evidence persistence boundary that accepts authenticated adapter identity/version and links the path to its validation/specification/candidate inputs. `persist_classification` should require that retained relationship rather than trusting a boolean embedded in the payload; tests should prove that manually constructed paths, unknown adapter IDs, and mismatched adapter versions remain unconfirmed.

## Audit failure rolls back successful policy outcomes

**High · confirmed.** `persist_policy_outcome` inserts the candidate successor, decision projection, and each supplied audit failure in one transaction (`artifact_repository.py:433-510`). `_atomic` rolls back the entire transaction on any exception (`artifact_repository.py:137-146`). The focused test explicitly codifies the loss at `tests/unit/ecatsl/test_artifact_repository.py:120-155`: an invalid audit-failure relationship causes both the candidate successor and policy decision to disappear. Requirement 3.9 instead requires retaining the applied policy outcome and flagging the candidate version when provenance recording fails.

Separate the authoritative policy outcome/candidate commit from best-effort audit-detail retention, or catch audit projection failures and commit a deterministic missing-audit marker in the same authoritative record. Add a test where policy evaluation succeeds, audit metadata persistence fails, and reopen/replay still returns the successful outcome plus the exact missing element.

## Finding metadata failure rolls back the classification

**High · confirmed.** `persist_classification` validates every lineage ID and writes the classification plus relationship rows inside one `_atomic` block (`artifact_repository.py:563-643`). A missing specification, validation, explanatory-support, or path row raises before the classification is inserted; a later projection failure rolls the inserted artifact back. There is no fallback that commits the already-made classification with `missing_metadata`, despite Requirement 4.7 requiring exactly that behavior.

Persist the classification decision independently of optional lineage projections, then retain every available relationship and append deterministic missing-element flags for failures. The API needs a result that distinguishes classification success from partial metadata retention, with tests that inject each projection failure and verify the classification identity/status survives restart.

## Finding lineage drops and misclassifies relationships

**Medium · confirmed.** `persist_classification` checks each specification and explanatory-support identity only with `_require_artifact` at `artifact_repository.py:585-588`, so unrelated artifact types satisfy those fields. It then selects `classification.specification_ids[0]` at lines 603-606 and stores only that value in `ecatsl_finding_lineage`; there is no many-to-many specification or explanatory-support projection analogous to candidate and validation tables. The canonical payload still contains the tuple, but projection-based lineage queries silently omit every specification after the first and cannot enforce that explanatory support is catalog-derived.

Add typed `_require_specification` and `_require_explanatory_support` checks, validate candidate/specification/validation/path consistency, and add relationship tables for all specification and explanatory-support IDs. Cover multiple specifications, wrong-type IDs, and cross-candidate lineage in tests.

## Stored type names cross the SQLite trust boundary

**High · confirmed.** Artifact types are persisted as `<module>:<qualname>` (`artifact_repository.py:107-109`). Untyped load and every idempotency replay call `importlib.import_module` on that database value and traverse arbitrary attributes before checking `issubclass(..., Artifact)` (`artifact_repository.py:198-217`, `225-247`). A locally corrupted or replaced SQLite file can cause import-time code execution, and a legitimate artifact becomes unloadable after its Python class moves even though its schema data remains valid.

Replace dynamic imports with a closed, versioned discriminator-to-model registry and reject unknown discriminators without importing them. On load, also cross-check the requested row key, stored hash, discriminator, and reconstructed artifact identity; add corrupted-row tests for unknown modules, malformed result lists, mismatched payload identities, and renamed-model compatibility.

## Historical schema-v1 upgrades are not covered

**Medium · confirmed.** Schema v2 adds `ecatsl_idempotency_key` as an append-only migration at `src/ecatsl/schema.py:309-325`, but `test_populated_legacy_catalog_migrates_idempotently_without_data_loss` starts from catalog tables with no ECATSL migration ledger and installs all current migrations at once (`tests/unit/ecatsl/test_schema.py:123-151`). The suite never opens a database produced by the previously shipped v1 DDL/checksum, containing populated v1 artifacts and a v1 ledger row, and upgrades only that database to v2. Because startup rejects any recorded v1 checksum mismatch, an accidental edit to `_V1_STATEMENTS` would make existing databases fail before v2 is applied.

Check in a minimal historical-v1 SQLite fixture or frozen v1 DDL/checksum builder, populate representative artifact/projection rows, then run the current installer and assert those rows remain queryable, the original v1 ledger row still validates, and only the v2 table/ledger row is appended.
