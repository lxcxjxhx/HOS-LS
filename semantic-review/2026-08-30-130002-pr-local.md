# Crash-recovery and compare-and-append persistence for ECATSL task 2.3

Task 2.3 adds bounded SQLite writer acquisition, durable operation journals, compare-and-append candidate updates, restart recovery, and migration journaling after schema v4. The compare-and-append transaction prevents two SQLite writers from committing successors from the same observed head, but the journal does not preserve legal state semantics under replay, interruption, or concurrent recovery. Optional classification replay is checked against the original request, while policy replay remains type-only. **Watch for:** **High · confirmed** in-flight `BaseException` paths retain the SQLite transaction and lock; **High · confirmed** a failed replay can change an already committed journal to `FAILED`; **Medium · confirmed** recovery can label a still-active write or migration `INTERRUPTED`; **High · confirmed** policy replay can return a different valid result tuple; **Medium · confirmed** successful append replay reports the predecessor as the actual head; **Medium · confirmed** no-key writes create permanently unlinked journal growth.

## High-level view

The journal’s `STARTED` event is committed before the artifact transaction begins. **High · confirmed:** repository and future-migration write bodies catch `Exception`, not `BaseException`, so an interruption after `BEGIN IMMEDIATE` can bypass rollback while repository bookkeeping is cleared.

The same deterministic transaction row is reused for every idempotent replay. **High · confirmed:** no new attempt state follows `COMMITTED`, yet any replay exception appends `FAILED`, making the latest state contradict the durable artifact and idempotency result.

Recovery has no process, connection, or lease identity. **Medium · confirmed:** elapsed time alone can turn another live writer’s `STARTED` into `INTERRUPTED` during the committed-journal/write-lock gap, and future migration recovery interrupts any observed `STARTED` without a stale threshold.

Policy and classification metadata failures can change persisted content relative to the original request fingerprint. **High · confirmed:** classification validates the replayed augmentation, but policy replay accepts any candidate/decision/failure sequence with the expected runtime types.

**Medium · confirmed:** successful compare-and-append replay sets `actual_head_id` to the replayed record’s predecessor rather than the committed successor.

**Medium · confirmed:** every no-key call creates a random transaction plus `STARTED` and terminal events, but no public lookup or result linkage makes those append-only rows useful for retry or result identification.

<summary>Issues (7)</summary>

1. **High · confirmed — In-flight interruption rollback hole** — `BaseException` after writer acquisition leaves the transaction and SQLite lock open. Roll back on every `BaseException`, re-raise it, and retain the durable `STARTED` event for restart recovery.
2. **High · confirmed — Committed journal can become failed** — replay errors append `FAILED` to the original committed transaction. Track replay attempts separately and enforce terminal-state transition rules.
3. **Medium · confirmed — Live transaction misclassified as interrupted** — recovery relies on event age without proving owner death, while migration recovery has no stale check. Add owner/lease semantics and recheck migration applicability under the writer lock.
4. **High · confirmed — Policy replay result substitution** — policy replay validates only model types, not request semantics, lineage, cardinality, or failure relationships. Add a semantic replay validator equivalent to classification’s.
5. **Medium · confirmed — Stale head in successful replay result** — append replay returns the predecessor as `actual_head_id`. Return the committed successor ID or a deliberately queried current head.
6. **Medium · confirmed — Unlinked no-key journal growth** — each no-key write permanently adds at least three rows without retry or result lookup value. Require retry keys, expose/link transaction results, or define bounded retention.
7. **High · confirmed — Crash-boundary coverage gap** — interruption tests fire before `BEGIN IMMEDIATE`, so they cannot detect leaked in-flight transactions or concurrent recovery races. Add caught-`BaseException`, subprocess-exit, concurrent-constructor, and concurrent-migration tests.

## In-flight interruption leaves the SQLite writer transaction open

**High · confirmed.** `_atomic` commits `STARTED`, acquires `BEGIN IMMEDIATE`, performs the write, and catches only `Exception` at `src/ecatsl/artifact_repository.py:489-522`. A `BaseException` after writer acquisition skips `rollback()` and reaches `finally`, which clears `_active_transaction_id`; the connection remains `in_transaction` and holds its SQLite writer lock until close or explicit rollback. Future migrations have the same boundary at `src/ecatsl/schema.py:709-741`: writer acquisition is at line 712, while rollback is reachable only from `except Exception` at line 731.

The repository interruption test fires at `transaction.after_started` (`tests/unit/ecatsl/test_artifact_repository.py:832-836`), before `_atomic` acquires the writer transaction. The migration test fires at `migration:<version>:after_started` (`tests/unit/ecatsl/test_schema.py:595-598`), before writer acquisition and DDL. Catch `BaseException` around each in-flight transaction solely to roll back and re-raise; retain `STARTED` rather than recording `FAILED` for interruption. Verify a second connection can acquire `BEGIN IMMEDIATE` after a caught interruption, and use a subprocess exit to exercise actual connection-loss rollback.

## A replay failure rewrites a committed transaction’s latest state

**High · confirmed.** `_prepare_transaction` appends a fresh `STARTED` only when the prior state is `FAILED` or `INTERRUPTED` (`artifact_repository.py:459-467`). Replays of `COMMITTED` or `REPLAYED` operations therefore run under the original transaction ID without an attempt boundary. If replay loading, validation, or finalization raises, `_atomic` calls `_record_transaction_failure` (`artifact_repository.py:516-518`), appending `FAILED` even though the artifact and `ecatsl_idempotency_key` result remain committed.

The schema constrains only the state vocabulary, not transitions (`src/ecatsl/schema.py:491-506`), permitting `STARTED → COMMITTED → FAILED`; `transaction_state` then falsely advertises failure and the next call treats the committed operation as retryable. Add attempt identity or append `STARTED` for each invocation, and reject transitions that alter a durable commit outcome.

## Timestamp recovery can interrupt a live owner

**Medium · confirmed.** `recover_interrupted_transactions` appends `INTERRUPTED` based only on the latest `STARTED` timestamp (`artifact_repository.py:527-556`). `STARTED` is committed at line 468 before writer acquisition around line 505. A process pause, scheduler stall, or lock wait in that gap lets another constructor append `INTERRUPTED`; the original owner can resume and append `COMMITTED`, producing a false `STARTED → INTERRUPTED → COMMITTED` history.

Future migrations convert any latest `STARTED` to `INTERRUPTED` and append another `STARTED` without a lease or stale check (`schema.py:649-651`). Migration applicability is read before the per-migration writer transaction (`schema.py:679-703`) and not rechecked after acquisition, so concurrent installers can execute the same pending migration; one can commit while the other records `FAILED` against their shared transaction ID. Add owner/lease identity or another owner-death proof, and re-read schema version under the migration writer lock.

## Policy replay is not bound to the policy request

**High · confirmed.** `persist_policy_outcome` fingerprints the original decision, candidate, expected predecessor, and supplied failures, then can derive different artifact identities for missing optional metadata. Its replay branch at `artifact_repository.py:1177-1191` supplies no expected result IDs and checks only `CandidateRecord`, `PolicyDecisionRecord`, and zero or more `AuditFailureRecord` types. Candidate lineage, policy kind/version/outcome, missing elements, failure relationships, cardinality, and ordering are not compared with the request.

Classification handles the same dynamic-metadata problem through `_validate_classification_replay` (`artifact_repository.py:1467-1469`, `1723-1765`). Add an equivalent policy validator so a substituted durable result list cannot redirect an unchanged idempotency key to another valid policy outcome.

## Successful append replay reports a stale actual head

**Medium · confirmed.** The initial compare-and-append returns the new record ID as `actual_head_id`, while replay returns `replayed.predecessor_id` (`artifact_repository.py:929-938`). A root-to-successor replay therefore reports the root as the actual head although the successor is durable. Return `replayed.artifact_id`, or query the current durable head if the field intentionally means live state, and assert every replay result field.

## No-key calls produce unqueryable append-only journal amplification

**Medium · confirmed.** Without an idempotency key, `_transaction_id` generates a UUID (`artifact_repository.py:374-379`), `_prepare_transaction` inserts a permanent transaction and `STARTED` event (`artifact_repository.py:428-445`), and `_atomic` appends a terminal event (`artifact_repository.py:508-515`). `_remember_idempotency` stores no artifact linkage, `transaction_state` requires `(operation, idempotency_key)` (`artifact_repository.py:563-579`), and the API does not return the random transaction ID.

A normal no-key write adds three append-only rows that cannot drive retry or identify its result; conflicts add `ecatsl_transaction_result`. Require a retry key for durable logical-operation journaling, return and link transaction results, or define bounded retention compatible with the audit contract.

## Crash tests stop before the real SQLite interruption boundary

**High · confirmed — Not tested.** The writer race uses one file-backed `ArtifactRepository` connection per thread (`tests/unit/ecatsl/test_artifact_repository.py:745-755`), and the lock test holds `BEGIN IMMEDIATE` on a separate connection (`test_artifact_repository.py:796-804`), so ordinary lock concurrency is realistic. Crash simulation occurs only before the in-flight writer transaction; there is no concurrent-constructor recovery, concurrent migration installer, replay-failure transition, no-key growth, or full-field successful replay case. Add those cases while preserving independent SQLite connections.
