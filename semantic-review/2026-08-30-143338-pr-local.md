# Legacy retry journal terminalization (v4)

This revision advances the ECATSL schema to v7 with one append-only migration that closes the legacy v4 `STARTED → FAILED → STARTED` upgrade hole. V7 appends a deterministic, null-attempt `LegacyJournalUpgrade` `INTERRUPTED` event only when the transaction's absolute latest event is a legacy `STARTED`; it leaves every prior migration definition in place. That preserves the attempt-based recovery model introduced in v5 while making old null-attempt retries terminal and repeatable to install. **Watch for:** **likely — non-blocking** the owned-attempt exclusion is proven by the v7 predicate but has no dedicated migration fixture; a future predicate refactor could regress it without a focused test.

**Verdict**: APPROVED

## High-level view

The upgrade keeps historical journal semantics split by ownership. V6 still handles an uncomplicated terminal-less legacy start; V7 addresses only the legacy retry pattern V6 intentionally could not select. Since v7 requires the globally newest event to be null-attempt `STARTED`, an active v5+ attempt is an exclusion boundary rather than something V7 can terminalize.

The installer continues to treat built-in migrations as atomic schema changes with no retry journal rows. Migrations beyond the built-in schema version use durable per-attempt journal entries, recover only proven-dead owners, and recheck the version ledger after the writer lock is acquired.

The earlier runtime corrections remain intact: a legacy durable idempotency result wins over later attempt-local replay failure, duplicate policy audit keys fail before writes and behave identically on retry, terminal events are constrained to their owning transaction, and `UNKNOWN` process liveness remains non-recoverable. The static `PathEvidence` confirmation boundary still requires an authorized supported run, complete path-bound candidate/specification/validation lineage, and an absent or failed sanitizer.

## V7 closes only the stranded legacy retry

`_V7_STATEMENTS` selects a transaction only when the event with its maximum sequence has both `attempt_id IS NULL` and `state = 'STARTED'` (`src/ecatsl/schema.py`). It then appends exactly one null-attempt `INTERRUPTED` event with `failure_type = 'LegacyJournalUpgrade'`. This corrects a v4 history of `STARTED → FAILED → STARTED`: V6 sees the earlier `FAILED` and leaves the final start alone, then V7 adds the fourth event.

The same absolute-latest-event guard is the ownership boundary. A v5+ running attempt contributes an owned `STARTED` as the latest event, so V7's selection cannot match and cannot attach a legacy terminal after it. A simple terminal-less v4 start is already ended by V6; its V6 terminal then excludes V7. Once either migration has appended a terminal, subsequent installation finds no pending version and appends nothing. The regression tests cover the simple-start and retry histories and verify the second installation remains at two and four events respectively.

## Migration history stays append-only while extension migrations retain recovery

`SCHEMA_VERSION` is now 7 and `MIGRATIONS` appends `_V7_STATEMENTS` after the existing v1–v6 entries; the pre-v7 statement tuples are not rewritten by the fix. The migration ledger validates every recorded migration name and checksum as an exact contiguous prefix, protecting deployed v1–v6 definitions from replacement. The frozen historical v1 checksum regression still passes; repository metadata is absent from this task copy, so a mechanical diff against `main` for separately proving every v2–v6 checksum was unavailable.

Built-in migrations remain journal-free because each DDL/version-row change is one SQLite transaction. The `migration.version > SCHEMA_VERSION` gate keeps durable retry attempts for extensions only, after the v5 attempt tables exist. Those extensions register a start before work, recover only a confirmed-dead owner, and recheck applicability under `BEGIN IMMEDIATE`; interrupted and concurrent extension-install regressions cover both recovery and replay paths.

## Earlier journal and confirmation protections remain preserved

`transaction_state` recognizes legacy null-link idempotency ownership by operation, key, and request hash, so a durable historical result remains logically `COMMITTED` when a later replay is `REPLAYED` or `FAILED`. Policy persistence rejects duplicate `missing_element` values before opening an atomic write, preventing both artifacts and idempotency/journal rows from being created; retry produces the same rejection.

The v6 trigger requires an attempt-bearing event to name that attempt's transaction, while both repository and migration recovery operate by attempt and only append `INTERRUPTED` for `DEAD`. Windows failures to open or query a process yield `UNKNOWN`, which neither recovery path treats as permission to interrupt. The confirmation path still rejects self-asserted or unsupported paths and requires an authorized persisted static binding, matching adapter identity, complete candidate/specification/validation inclusion, and a non-blocking sanitizer before `CONFIRMED` can be retained.

## Regression evidence and remaining boundary coverage

The focused schema and repository suite passes 49 tests, and `python -m compileall -q src/ecatsl tests/unit/ecatsl` passes. The provided recent full ECATSL result is 63 passing tests. The new migration coverage directly exercises simple legacy `STARTED`, the failed-then-restarted legacy sequence, and idempotent reinstallation. It does not directly execute the owned-attempt exclusion described in the issue summary, although the current maximum-sequence predicate verifies that behavior.
