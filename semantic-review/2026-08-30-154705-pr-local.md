# ECATSL policy boundary and populated-catalog recovery (v5)

Task 2.4 introduces deterministic acceptance and validation decisions, carrying the selected policy version, candidate state/confidence effect, sorted complete input identities, and audit metadata without granting confirmation authority. Task 3.1 exercises those changes against a populated CWE/NVD SQLite database: failed extension DDL rolls back atomically, a `BaseException` leaves a recoverable started attempt, restart terminalizes that attempt, and repeated install/repository writes replay idempotently. The persisted static-path confirmation gate still requires a supported, authorized adapter run, complete path-bound candidate/specification/validation lineage, and a non-blocking sanitizer. **Watch for:** **likely — blocking** provider-specific LLM/RAG provenance such as `openai` is not classified as non-confirmatory, so it can satisfy `independent_evidence` without an explicit origin/ranking policy condition.

**Verdict**: NEEDS_CHANGES

## High-level view

The policy result is deliberately a pure decision record rather than a proof artifact: acceptance can only reach `ACCEPTED`, validation can retain or reduce that state, and an already rejected candidate is pinned to `REJECTED` with zero confidence. Catalog, NVD, RAG, LLM, discovery, templates, and endpoint labels are intended to be non-confirmatory; the implementation relies on a small origin-token allowlist to enforce that boundary, which leaves provider-origin evidence outside the restriction.

The migration scenario keeps the shared catalog usable throughout independent ECATSL schema installation. Built-in migrations stay atomic and journal-free; extension migrations journal an owned attempt, recover only a proven-dead owner, recheck applicability under the writer lock, and make repeat installation a no-op. The Task 2.2 confirmation path remains independent from policy acceptance and catalog data.

## Origin tokens leave an LLM/RAG acceptance path open

**Likely — blocking.** `evaluate_acceptance` treats evidence as independent unless `_is_non_confirmatory` finds one of the literal tokens in `Evidence.provenance.origin`. The set includes `llm` and `rag`, but not provider or implementation identifiers. Consequently, an otherwise linked `Evidence` record with `origin="openai"`, `origin="anthropic"`, or a concrete hybrid-retriever name has `has_independent_evidence=True`; a policy containing only `independent_evidence` accepts it. This does not bypass `persist_classification` into `CONFIRMED`, because that path still requires authorized `PathEvidence`, but it violates the requested policy boundary that catalog/NVD/RAG/LLM/discovery inputs be used only under explicit origin/ranking conditions.

The existing parametrized test covers the normalized labels `catalog`, `nvd`, `rag`, `llm`, and `discovery`, which explains why the provider naming boundary is untested. Classify each evidence source at construction or normalize origins against a closed source taxonomy before evaluation. A regression should demonstrate that provider-specific LLM and retriever origins leave `independent_evidence` unmet unless separately accompanied by qualifying repository/static evidence, while an explicit `origin:<normalized-source>` ranking condition remains the only permitted direct use.

</details>
