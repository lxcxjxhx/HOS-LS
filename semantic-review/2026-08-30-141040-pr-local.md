# ECATSL transaction recovery and confirmation-boundary re-review (v3)

This pass verifies the five v2 findings and the follow-up migration design across the repository schema, journal, and focused regression tests. Legacy v2/v3/v4 idempotency rows with null transaction links now preserve a logical `COMMITTED` result through replay failures; duplicate policy failures are rejected before any artifact, idempotency, or journal write; and `UNKNOWN` process liveness no longer interrupts an attempt. Built-in v1-v6 installation avoids no-key journal rows, while extension migrations retain durable attempts, crash recovery, and writer-lock applicability rechecks. **Watch for:** **Medium · confirmed** v6 terminalizes only transactions with no historical terminal at all, leaving a later terminal-less v4 retry permanently unrecoverable when that transaction has an earlier failed or interrupted attempt.

**Verdict**: NEEDS_CHANGES

## High-level view

The runtime journal now separates attempt-local terminal events from the logical operation result. The null-link fallback in `transaction_state` recognizes legacy idempotency ownership by operation, key, and request hash, so `REPLAYED` and `FAILED` attempts cannot overturn a durable legacy artifact result.

V6 converts a simple terminal-less v4 transaction into a deterministic `INTERRUPTED` outcome without inventing an attempt owner. Its selection predicate, however, treats any earlier terminal in the transaction as proof that every legacy start completed; a failed retry followed by a crash therefore remains outside both the migration conversion and ordinary attempt recovery.

The baseline installer keeps v1-v6 atomic and journal-free, whereas extensions beyond the built-in version journal their durable attempts before executing and recheck the migration ledger after obtaining the writer lock. The task-2.2 confirmation gate remains trust-bound: only a persisted supported static run, matching path binding, complete candidate/specification/validation lineage, and an absent or failed sanitizer can produce `CONFIRMED`; explanatory support does not satisfy those conditions.

## V6 mistakes an earlier failed attempt for completion of the latest v4 retry

**Medium · confirmed.** The v6 data migration declares that it converts a transaction “whose latest legacy attempt never completed,” but its `INSERT … SELECT` accepts a transaction only if it has a null-attempt `STARTED` event and has no non-`STARTED` event anywhere in its history (`src/ecatsl/schema.py`, `_V6_STATEMENTS`). A valid historical sequence of `STARTED → FAILED → STARTED` therefore fails the second predicate because the middle `FAILED` exists. The final `STARTED` receives neither the deterministic `LegacyJournalUpgrade` terminal nor an `ecatsl_transaction_attempt` row.

That row is then invisible to normal recovery, which begins at `ecatsl_transaction_attempt` in `ArtifactRepository.recover_interrupted_transactions` and migration recovery. The logical operation is left with a final `STARTED` journal state forever, even though the upgrade is intended to make terminal-less v4 work deterministic. The existing v4 upgrade test covers only a single `STARTED`, so it cannot detect the prior-terminal sequence.

Select the latest event for each transaction (or require that no terminal follows the relevant legacy `STARTED`) before appending one `INTERRUPTED` event. Add a historical v4 fixture with `STARTED`, `FAILED`, then `STARTED`; after v6 it should have exactly one added `LegacyJournalUpgrade` terminal, and a second installation must add none.

</details>
